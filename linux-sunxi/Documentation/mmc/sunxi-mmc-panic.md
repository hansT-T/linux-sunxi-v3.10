# T3 eMMC panic 写入接口：从基础 C 到理解驱动

本文对应同一源码树的 `drivers/mmc/host/sunxi-mmc.c` 与 `include/linux/mmc/sunxi-mmc-panic.h`。读者只需要先理解 C 的变量、数组、指针、结构体、函数和循环；内核与硬件知识会在使用时说明。

## 1. 这次做到了哪一步

这次把原先的上板测试代码整理为可供 pstore 后端调用的底层接口。它接收一段内存中的数据，在 fatal panic 环境下，通过 T3 的 sdc2/v4p5x 控制器写到提前指定的 eMMC 区域。

它**还不是完整的 pstore 后端**：本树是 Linux 3.10.108，`fs/pstore/` 没有现代内核的 `blk.c`/`zone.c`。本次没有新增 `pstore_register()`、日志记录格式、开机扫描和 `/sys/fs/pstore` 文件恢复。底层写接口准备好以后，下一步才是实现这些内容。

代码不会自动触发 panic，也不会自动向旧测试分区写固定数据。调用者必须先显式准备一个专用日志区域，再在真正的 panic 回调中调用写接口。

### 两份 sunxi-mmc 文件如何理解

- `sunxi-mmc-v1.c` 是用户提供的实际运行旧版，本次保持原样。
- 当前 `sunxi-mmc.c` 的普通驱动主体属于本参考树较新的 BSP 版本。CMD23、加密、读超时、busy 处理、时钟、电压及控制器支持等差异，不是此次 pstore 测试新增的逻辑。
- 本次在当前文件上移除测试并整理接口，保留其普通驱动主体。不能因为本次重构完成，就认为它与旧版驱动完全等价。
- 回到实际产品工程时，应移植这里的 panic 部分，并对照该工程的 host 字段、中断处理、头文件与配置进行编译。不能只复制整个较新文件覆盖旧版。旧版还引用了本参考树没有的 `mmc->hw_reset_cnt`，也说明两套源文件不能任意混搭。

## 2. 先建立一幅完整的图景

正常写磁盘的大致路径：

```text
应用程序或内核调用者
  -> 文件系统/块设备层
  -> MMC 核心提交请求
  -> sunxi 控制器通过 DMA 搬运数据
  -> 硬件中断通知完成
  -> 等待中的调用者被唤醒
```

panic 表示内核已进入不可恢复的故障处理。其他 CPU 可能已经停止，中断被关闭；原来持有锁的 CPU 也可能不会再释放锁。此时再走普通路径，可能永远等不到完成通知。

本次的路径：

```text
正常运行：选定日志区域 -> prepare -> 保存以后必需的信息

fatal panic：上层提供内存数据
  -> 检查参数与设备状态
  -> 第一次写时接管控制器
       -> 有旧请求：先等完成，必要时中止支持的多块传输
       -> 没有旧请求：确认控制器与卡就绪
  -> 每 512 字节发送一次 CMD24
  -> CPU 把数据写入 FIFO
  -> 轮询直到命令、数据、卡状态都满足完成条件
  -> 返回结果

重启：上层通过普通块设备路径读取并解析上次记录
```

“轮询”就是在有界循环里不断读一个状态，例如 `while` 或 `for` 中检查某个位是否变成 1。它不依赖中断唤醒。

## 3. 三个接口先学会怎么用

包含头文件：

```c
#include <linux/mmc/sunxi-mmc-panic.h>
```

| 接口 | 调用环境 | 作用 | 返回值 |
| --- | --- | --- | --- |
| `sunxi_mmc_panic_prepare(card, start_sector, nr_sectors)` | 正常进程上下文，可睡眠 | 绑定卡与专用区域、检查能力、保存配置 | 成功 0，失败负错误码 |
| `sunxi_mmc_panic_write(sector, buf, bytes)` | fatal panic，其他 CPU 已停止，本地中断关闭 | 首次接管后写入若干完整扇区 | 全部成功 0，失败负错误码 |
| `sunxi_mmc_panic_unprepare(mmc)` | 正常进程上下文，可睡眠 | 撤销配置、等待已进入的读者退出、释放引用 | 无返回值 |

本实现只允许一个活动的准备上下文；重复 prepare 返回 `-EBUSY`。prepare/unprepare 调用者不能已经持有 MMC host claim，且必须持有有效的 card 生命周期引用，并与驱动/卡移除过程串行。底层 remove 也会撤销上下文，但这不能替代后端自己的生命周期管理。

### 扇区地址与字节数不要混淆

本实现一个扇区是 512 字节：

```text
prepare 的 start_sector：整块 eMMC user area 上的绝对扇区号
prepare 的 nr_sectors：这块日志区域一共有多少个扇区
write 的 sector：相对于日志区域开头的扇区号
write 的 bytes：本次内存数据长度，单位是字节
```

假设只用于解释的区域从扇区 10000 开始、有 32 个扇区：

```c
/* 仅说明单位；10000/32 不是可以直接在板上使用的分区配置。 */
ret = sunxi_mmc_panic_prepare(card, 10000, 32);
/* ……以后进入 fatal panic…… */
ret = sunxi_mmc_panic_write(2, data, 1024);
```

第二个调用写的是绝对扇区 10002、10003。接口不需要调用者每次重新计算整盘地址。

`bytes` 必须是 512 的倍数，范围为 512～4096；`buf` 不需要四字节对齐。超过 4096 字节的日志由上层拆成多次调用。4 KiB 是对单次调用的限制，不是整个日志区的容量限制，也不意味着 4 KiB 能一次原子写入。

原测试代码的 `15237120/32768` 只属于之前验证过的板卡布局，本次不再硬编码。真实区域应从产品已确认的分区布局取得，而且必须独占，不能与文件系统、其他日志后端或测试程序共用。prepare 只能核对整卡容量，无法从两个整数判断“这是不是你想要的分区”。

## 4. 从 C 结构体理解上下文

`struct sunxi_mmc_panic_context` 是一份跨函数保留的数据集合，可以把它理解成“写日志前准备好的工作记录”。

| 字段 | 含义 | 为什么需要 |
| --- | --- | --- |
| `host` | 控制器对象指针 | 找到寄存器和驱动状态 |
| `card` | eMMC 卡对象指针 | 确认当前仍是原来那张卡 |
| `start_sector/nr_sectors` | 专用区域 | 统一地址换算和边界检查 |
| `status_arg` | `RCA << 16` | CMD13 查询卡状态的参数 |
| `card_sectors` | 准备时的整卡容量 | 检查卡身份/配置变化 |
| `timer_hz` | 硬件计数器每秒计数 | 在中断关闭时计算超时 |
| `ios` | 时钟、位宽、时序、电压快照 | panic 时确认运行条件仍与准备时一致 |
| `writing` | 原子使用标志 | 拒绝重入，不能等待另一个调用 |
| `taken_over` | 是否已完成首次接管 | 同一 panic 的第二段日志无需再处理旧请求 |
| `error` | 已发生的错误 | 状态不确定后停止进一步写入 |

`ctx->field` 是通过结构体指针访问成员，等价于 `(*ctx).field`。

`kzalloc(sizeof(*ctx), GFP_KERNEL)` 分配足够容纳一个结构体的内存，并清零。`sizeof(*ctx)` 不依赖手工填写结构体大小，增减字段后仍然正确。分配发生在 prepare 中，panic write 不分配内存。

## 5. prepare 为什么只能在正常阶段执行

prepare 按以下顺序工作：

1. 用普通 mutex 串行化准备/释放，确保不会有两个调用者同时替换全局配置。
2. 确认目标就是 probe 识别到的 sdc2/v4p5x host。
3. 分配上下文；claim MMC host，防止普通请求同时改变卡状态。
4. 保持 MMC 时钟引用，检查卡类型、寻址方式、扇区大小、硬件分区、缓存和总线时序。
5. 用减法校验整个区域位于卡容量内。
6. 检查 ARM 硬件计数器确实在递增。
7. 通过普通 MMC 路径发 CMD13，确认卡 ready 且处于 TRAN。
8. 保存快照、取得 card 引用，最后发布上下文指针。
9. 释放 host claim，使正常 I/O 继续；保留时钟引用直到 unprepare。

claim host 表示“这一小段正常初始化期间，我独占 MMC 请求流程”。它可能等待，所以不能在 panic 路径使用。

保持时钟引用是为了防止普通 MMC 空闲时钟门控在准备完成后立即关掉卡时钟。这不等于禁止系统 suspend，也不保证电源永远存在：panic 时仍检查电源、时钟和配置。产品若需要休眠期间也可靠记录，要单独设计电源管理，不能靠本接口凭空启动已断电的设备。

为避免访问已关闭时钟的寄存器，驱动在 `set_ios`、CMD6 卡配置修改、电压切换、卡硬件复位、shutdown 和 suspend 的入口，先使 `sunxi_mmc_panic_valid` 失效。panic 在任何 MMIO 前检查这个软件标志。之后即使总线恢复原来的数值，也需要上层在稳定运行状态下执行 `unprepare + prepare`，刷新上下文；不会自动恢复旧配置的有效性。suspend 期间禁止 prepare，只有成功 resume 后才解除这个禁止。失败的电源转换保持保守禁用，直到完成恢复或重启。上层的准备/释放也必须与 PM 串行。

### 为什么要求关闭 eMMC cache

CPU 把数据交给控制器、控制器把数据交给卡、卡把数据写入持久介质，是不同阶段。如果卡启用了写缓存，命令完成不一定意味着缓存已经刷新。本次沿用原验证范围，拒绝 cache enabled，不在 panic 中临时调用会等待普通请求的缓存刷新函数。

这也不能推出“任何突然断电都绝对安全”：仍需通过断电测试验证具体卡的行为，上层记录格式也必须能识别残缺数据。

### 为什么要求 user area

eMMC 有 user area、boot、RPMB 等不同硬件区域。相同扇区号在不同硬件区域不是同一位置。这个实现只验证了 user area，因此拒绝其他硬件分区，避免把同一个数字写到错误的地方。

卡配置通常通过 CMD6 修改。普通驱动会先让硬件执行 CMD6，再更新内存中的 `ext_csd` 字段；两步之间如果恰好 panic，仅检查内存快照可能遗漏已经完成的硬件分区切换。于是普通 request 在发 CMD6 前就使准备状态失效，直接封住这个窗口，而不是尝试在 panic 里猜当前硬件分区。之后由上层在配置稳定时重新准备。

## 6. 为什么保留这些判断，却删除测试判断

判断可以按用途理解：

- **接口边界**：空指针、长度、范围。防止调用者给错参数。
- **运行环境**：中断、host 阶段、时钟、卡配置。确保当前可以执行已验证流程。
- **硬件结果**：错误位、busy、完成位。确保刚发出的操作真的完成。
- **测试覆盖**：是否命中指定 pattern、DMA 是否恰好处于测试要求的进度、是否强制走某条分支。

前三类决定功能是否正确，需要保留。最后一类只用于之前上板测试，这次移除了。不能用“减少 if”作为唯一目标；真正的简化是让每个判断都能回答一个具体的正确性问题。

边界判断示例：

```c
if (sector >= ctx->nr_sectors ||
    bytes / 512 > ctx->nr_sectors - sector)
        return -ERANGE;
```

为什么不写 `sector + bytes / 512 > nr_sectors`？因为无符号整数相加可能绕回一个很小的值，错误地通过检查。先确认 `sector` 在范围内，再用剩余空间相减比较，就不需要冒险相加。

整个范围在第一条硬件命令前检查完，因此不会发生“前面写了几个扇区，才发现后面越界”。硬件故障导致的部分写入则仍然可能发生，两者要区分。

## 7. 原子操作、mutex 和 RCU 分别解决什么

### mutex：只管正常上下文

`sunxi_mmc_panic_lock` 保护正常的 prepare、unprepare 和 remove。拿不到 mutex 时可以睡眠等待；因此 write 不拿它。

### 原子标志：只试一次，不等待

```c
if (atomic_cmpxchg(&ctx->writing, 0, 1))
        /* 已有人使用，返回 -EBUSY */;
```

`cmpxchg` 是 compare and exchange：仅当旧值为 0 才改成 1，返回原来的值。检查与修改合成一个不可分割的动作，避免两个调用同时认为自己获得了使用权。

如果只是写 `if (!writing) writing = 1;`，两个执行者可能都在赋值前读到 0。panic 环境也不能自旋等待另一个执行者释放标志，因为对方可能已经停止。

### RCU：避免释放后还在使用指针

正常释放和 panic 读取可能在时间上交错。普通 C 代码中，先取得一个指针并不能保证指针指向的内存以后不会被释放。

这里的发布与释放流程是：

```text
prepare：填完所有字段 -> rcu_assign_pointer 发布
write：rcu_read_lock -> rcu_dereference 取指针 -> 使用 -> rcu_read_unlock
unprepare：把全局指针改为 NULL -> synchronize_rcu -> 释放内存
```

`synchronize_rcu()` 等待已进入的读者退出，只有正常上下文会调用。panic 写者不等待 RCU 宽限期。RCU 保护的是对象生命周期；`writing` 保护的是同一个对象中写入状态的串行使用，两者作用不同。

发布动作还保证读取方看见指针时能看见已经初始化的字段。不能把“先赋全局指针，再慢慢填字段”当成等价实现。

## 8. MMIO：为什么这些指针不能当普通内存随便读写

控制器通过一组寄存器与 CPU 通信。`host->reg_base` 是映射后的寄存器基地址，`REG_CMDR` 等名称对应不同偏移。

```c
value = mmc_readl(host, REG_STAS);
mmc_writel(host, REG_CARG, lba);
```

这些宏最终使用 `readl()/writel()`，表示读写设备寄存器。访问可能驱动硬件动作，不能替换成普通数组操作或随意合并。

常见位运算：

```c
value & FLAG        /* 检查某个位 */
value | FLAG        /* 设置某个位 */
value & ~FLAG       /* 清除某个位 */
```

`wmb()` 是写入顺序屏障。在写好命令参数、设置好控制信息之后，再启动命令，硬件才能看到正确的参数。它不是“睡一会”，也不是“把 eMMC 缓存刷到介质”。

`REG_RINTR` 中的很多状态位采用写 1 清零，即 W1C。向某位写 1 是确认并清除此事件，而不是把事件置为 1。发新命令前要区分旧事件和新事件，否则旧的 COMMAND_DONE 会让新命令被误判为完成。

## 9. 第一次 write 如何接管

公开 write 先校验参数，再读取已发布上下文。成功占用 `writing` 后：

1. 如果本次 panic 之前已经失败，直接返回保存的错误。
2. 如果 host 锁被持有，或请求已进入 busy、重试、手工 stop 阶段，返回错误。
3. 检查准备配置仍有效，再核对 card、时钟、电压、位宽、时序、硬件分区与缓存状态。
4. 第一次调用时运行 takeover，成功后设置 `taken_over`。
5. 循环调用单扇区写函数，完成所有扇区。
6. 释放 `writing`；若失败，保存错误，禁止后续写操作继续试探硬件。

第一次接管之后，旧的 `host->mrq` 可能还存在。我们不调用普通 MMC 完成函数，也不释放旧请求。因为这是 fatal panic，普通请求流程不会恢复。`taken_over` 正是为了第二次写时不把这份旧请求当成新的待接管请求。

因此，**不能仅仅在正常线程里关闭中断，然后调用此接口做普通写盘**；函数返回后也不能让正常 MMC I/O 继续运行。正常读写使用普通块设备接口。

## 10. 等待旧请求：把“硬件超时”和“我不想再等了”分开

如果 panic 前 DMA 已经启动，它可能仍在独立工作。先给它最多约 500 ms 的软件预算完成，有机会不破坏旧请求就接管。

等待函数检查当前请求与寄存器配置是否匹配。本版只处理已验证的标准 512 字节 CMD17/CMD24，及带 auto-stop 的 CMD18/CMD25；带 CMD23/sbc、流模式或其他命令不在接管范围。

完成不仅是 COMMAND_DONE。数据请求还需要 DATA_OVER，多块 auto-stop 请求还需要 AUTO_COMMAND_DONE；同时检查命令不再启动、数据状态机和卡 busy 消失、FIFO 空、IDMAC idle。

普通 IRQ 可能已经读取并清除了部分 RINTR。因此旧请求观察合并：

```c
raw = mmc_readl(host, REG_RINTR) | ACCESS_ONCE(host->int_sum);
```

`int_sum` 是普通驱动为当前请求累计的中断状态。合并只用于原请求；发送新的 CMD12/CMD13 后必须只看新命令自己的硬件状态。

两种失败不能混淆：

| 情况 | 含义 | 本实现怎么做 |
| --- | --- | --- |
| 软件等待预算耗尽，硬件未报告错误 | 本次轮询不再继续等待 | 对支持的多块数据传输尝试中止 |
| 控制器 timeout/CRC/error 或 IDMAC error | 硬件已明确报告失败 | 返回错误，不当成普通软件超时恢复 |

如果本轮采样同时发现完成和时间到，应优先接受完成。若数据已经传输结束、卡还在 programming busy，也不能把它当成尚未完成的数据阶段随意发 STOP。

## 11. DMA 到 PIO 的交接为什么不能只改一位

DMA 是由控制器自动读取内存描述符并搬运数据。PIO 是由 CPU 直接读写 FIFO。两者不能同时争用 FIFO。

中止前必须：

```text
关闭 DMAC.IDMA_ON
  -> 关闭 GCTRL.DMA_ENABLE
  -> 复位 DMA 接口并等复位位清零
  -> 复位 IDMAC 并等复位位清零
  -> 确认 DMA 状态机 idle
  -> 切换 ACCESS_BY_AHB
  -> 发送 CMD12 停止卡端旧传输
```

只清 DMA enable 不代表旧的总线访问已完全停止。复位期间还要保存并检查观察到的错误，不能用 reset 把错误痕迹抹掉后当作成功。

这里不做整个 host reset。整体复位会涉及时钟、总线宽度、延迟等已经验证的配置，panic 中重新初始化整条 MMC 链路会增加很多不确定性。

自然完成可能恰好发生在交接过程中。只有能明确确认的完成才能收尾；无法确认的竞态会保守返回错误，不能把它冒充一次成功的中止。

## 12. 为什么读中止和写中止不同

两者都发 CMD12，带 `STOP_ABORT_CMD`，不带 `WAIT_PRE_OVER`。后者会要求先等旧数据完成，而我们正是要停止旧数据传输。

### 中止读 CMD18

卡可能仍在把数据送入接收 FIFO。等待 CMD12 时，CPU 必须有界地读取并丢弃 FIFO 中残留数据，否则 FIFO 满可能阻碍旧传输停止。

这不是把旧请求读完，也不是给上层返回数据；只是为接管清理硬件通道。

### 中止写 CMD25

FIFO 可能还有尚未发送的数据，卡可能正在编程。先等 CMD12 完成、卡 busy 消失、数据状态机停止，然后只 reset FIFO，丢弃未发送部分。

不能一开始就清空 FIFO，也不能直接套用读路径。两条路径在安全时机上的区别是硬件要求，不是应该消除的代码重复。公共的 DMA 关闭与复位步骤则可以合并。

最后都用 CMD13 确认卡已经回到 `TRAN` 并且 `READY_FOR_DATA`。

## 13. 一次 512 字节 PIO 写的完整过程

主要命令先记住三个：

| 命令 | 用途 |
| --- | --- |
| CMD13 | 查询卡当前状态 |
| CMD24 | 写一个数据块 |
| CMD12 | 停止正在进行的传输 |

单扇区写依次执行：

1. CMD13 检查卡 ready/TRAN，并确认控制器、DMA、FIFO 处于可以发命令的状态。
2. 配置写 FIFO 阈值，保留原验证的整扇区缓冲策略。
3. 设置 `BLKSZ=512`、`BCNTR=512`。
4. 设置 `CARG=lba`，按顺序发出带数据和写标志的 CMD24。
5. 轮询：发现 FIFO 未满，就向 FIFO 写一个 32 位字。
6. 共写 128 个字，因为 `128 × 4 = 512`。
7. 检查命令完成、数据结束、FIFO 空、busy 消失及错误位。
8. 确认并清除本命令事件，再用 CMD13 确认卡可接收后续命令。

即使已经向 FIFO 写了 128 个字，也不能立刻返回成功。这只说明 CPU 把数据交给了控制器；卡是否接受、是否报错、是否还在忙，需要后面的状态检查。

### 为什么通过 memcpy 取一个 u32

上层 `buf` 是字节缓冲，地址未必能被 4 整除。直接把它强制转换成 `u32 *` 再解引用，在 ARM 上可能出现对齐问题。

```c
u32 word;
memcpy(&word, buf + offset, sizeof(word));
writel(word, fifo_address);
```

`word` 是对齐的局部变量，`memcpy` 允许从字节地址复制。这样无需为整个 4 KiB 再分配一个对齐缓冲，也不要求调用者理解控制器的四字节访问要求。

## 14. 为什么不能用 jiffies 无限等待

`jiffies` 通常依赖时钟中断更新。panic 中关闭中断以后，像下面的循环可能失去原本预期的超时效果：

```c
/* 不用于本接口 */
while (time_before(jiffies, deadline))
        /* 等状态 */;
```

这里使用 ARM arch timer 硬件计数器。频率是每秒的 tick 数，例如 10 ms 对应 `rate / 100` 个 tick。用“当前计数减起始计数”判断经过了多少时间，不需要等待时钟中断。

同时，每个循环还有次数上限。万一计数器后来停止，也不能永远卡住。次数上限是额外退出条件，不是精确计时器，因此循环可能比时间预算更早结束。

不同操作使用原验证范围内的预算：CMD13 约 10 ms，DMA/FIFO 复位各步骤约 10 ms，等待旧请求约 500 ms，读 STOP 约 100 ms，写 STOP 约 1 s，单扇区写约 500 ms。一次 4 KiB 包含八个扇区，并不只有一个 500 ms 的总预算；实际系统还要结合 watchdog 与重启策略评估总耗时。

没有 `CONFIG_ARM_ARCH_TIMER` 时，公开 prepare/write 返回 `-EOPNOTSUPP`，不会进入这些硬件路径。

## 15. 怎样与 3.10 pstore 接起来

本树 `include/linux/pstore.h` 的回调大致为：

```c
int (*write)(enum pstore_type_id type, enum kmsg_dump_reason reason,
             u64 *id, unsigned int part, int count, size_t size,
             struct pstore_info *psi);
```

这是上层后端的接口，不是本次的底层 write。`psi->buf` 保存框架交来的日志，`size` 是有效字节数，`part/count/id` 用于组织记录。`fs/pstore/platform.c` 可能多次调用后端，所以底层允许同一 panic 多次顺序写入。

建议先只处理 `PSTORE_TYPE_DMESG` 且 `reason == KMSG_DUMP_PANIC`。不要把这个接管接口用于普通 console 输出、可以恢复的 oops 或正常关机；这些场景不能假设其他 CPU 和普通 I/O 已经永久停止。

正常初始化时，上层需要：

1. 等目标卡与专用分区真正就绪，不把固定 late_initcall 时刻当成卡就绪事件。
2. 获取并确认专用区域，准备日志格式、序号及缓冲。
3. 通过正常块 I/O 扫描旧记录。
4. 调用底层 prepare。
5. 所有回调所需状态都已有效后，再 `pstore_register()`。

这棵树只允许一个已注册 pstore 后端；ramoops 已经占用时，新后端不能再次成功注册。注册还可能立即调用 read。当前树没有 `pstore_unregister()`，实际后端宜采用内建且生命周期稳定的设计，不能照搬现代内核模块卸载流程。

### 长度填充由上层做

例如一段有效日志是 700 字节：

```text
有效长度：700
实际写盘长度：1024（两个扇区）
第 0～699 字节：日志
第 700～1023 字节：清零填充
记录头另外保存有效长度 700
```

预先分配的缓冲必须容得下填充后的数据；不能只把 `size` 四舍五入后传入原来只有 700 字节的缓冲，那会越界读取内存。

下面只是接线示意，尚不包含可恢复的记录格式：

```c
/* scratch 在正常初始化时分配，容量至少 4096；回调必须串行使用它。 */
if (type != PSTORE_TYPE_DMESG || reason != KMSG_DUMP_PANIC)
        return -EOPNOTSUPP;
if (!size || size > SUNXI_MMC_PANIC_MAX_BYTES)
        return -EINVAL;

padded = (size + 511) & ~511U;
memset(scratch, 0, padded);
memcpy(scratch, psi->buf, size);
ret = sunxi_mmc_panic_write(next_sector, scratch, padded);
if (!ret)
        next_sector += padded / 512;
return ret;
```

真实后端还要对 `next_sector`、记录槽、`id/part/count` 和有效长度做管理。若要可靠识别断电留下的半条记录，应设计 magic、版本、长度、序号、校验值与提交标记。通常先写数据，全部成功后再写提交信息；启动扫描不能把未提交或校验失败的记录当成完整日志。这里只说明设计责任，不代表本次已经实现提交协议。

读取与删除在正常上下文走普通块 I/O，无需保留测试用 panic PIO 读函数。本树 pstore 在 read 返回正长度后会释放输出缓冲，后端应返回可由 `kfree()` 释放的记录副本。

## 16. 返回错误以后该怎么办

| 错误 | 常见含义 |
| --- | --- |
| `-EINVAL` | 缓冲为空、长度不合规或请求配置不匹配 |
| `-ERANGE` | 超出准备区域或卡容量 |
| `-ENODEV` | 尚未准备、卡已改变或计数器不可用 |
| `-EPERM` | write 调用时本地中断没有关闭 |
| `-EBUSY` | 重入、host 正处于不支持的处理阶段或硬件不空闲 |
| `-EHOSTDOWN` | 电源、时钟或总线配置不满足准备条件 |
| `-EOPNOTSUPP` | 卡配置、请求类型或构建配置不支持 |
| `-ETIMEDOUT` | 轮询超过时间/次数预算 |
| `-EIO` / `-EILSEQ` | 卡、控制器或 DMA 报错，CRC 错误或状态不满足成功条件 |
| `-EAGAIN` | 中止交接时出现自然完成竞态，无法确认安全接管；当前会话也停止后续写 |
| `-ELOOP` | 等旧请求达到循环次数上限，但尚未确认计时预算耗尽，不尝试中止 |

错误码只是原因分类，不能精确推导写入了几个字节。

一次调用若在第三个扇区失败，前两个扇区可能已经写入。公开接口不返回部分成功，也不承诺多扇区原子性。上层必须把整条记录视为未完成，不继续写“记录成功”的提交标记。

参数错误、未准备与入口重入没有取得写入所有权，不改变已准备会话。取得所有权后的设备检查、接管或传输失败会保存错误；后续调用直接失败。这个保守策略防止在未知硬件状态下继续发送命令。

## 18. 怎样自己一步步写出类似代码

建议按下列顺序学习，而不是先抄整个大函数：

1. **先写纸面契约。** 明确调用环境、单位、范围、返回值、失败后是否允许重试。没有契约，后面很容易把字节数当成扇区数。
2. **写范围检查。** 用普通 C 验证 0、最后一个扇区、刚好写满、越界和整数极大值。
3. **写正常 prepare。** 先只收集卡和区域信息，理解 claim、引用与发布顺序。
4. **写一个有界状态轮询。** 为正常结束、硬件错误、计时超时分别留出口。
5. **验证 CMD13。** 学会发送命令参数、启动位、响应、错误位与 W1C。
6. **验证空闲控制器上的一个 CMD24。** 只向专用测试区写一个扇区，用正常读盘核对。
7. **循环多个单扇区写。** 不急着增加新的多块写命令；上层循环就能支持 4 KiB。
8. **处理原请求自然完成。** 学会累计 IRQ 状态与硬件状态的关系。
9. **最后加入多块请求中止。** 分别验证读和写，保留 FIFO 与 busy 的顺序差异。
10. **检查多次调用与生命周期。** 同一 panic 不重复接管；释放不能先于在途读者退出。
11. **最后接 pstore 格式层。** 先确保原始字节能写对，再增加记录恢复协议。

每一步都应能回答三个问题：我依赖什么前提？怎样确认成功？如果这一步失败，下一步还可不可以做？这三个问题比记住某个寄存器数值更重要。

## 19. 编译与上板验证

### 本机验证的边界

本次工作环境是 macOS arm64，仓库附带的交叉 GCC 为 x86_64 Linux 可执行程序；当前树也没有产品 `.config` 和生成头文件。因此本机静态检查与接口模拟不能替代目标 ARM 内核构建，更不能声称已经完成重构后的硬件回归。

接口行为测试脚本位于 `tools/testing/sunxi-mmc-panic-interface.py`，从实际源码提取公开 write 函数，用模拟硬件辅助函数检查地址换算、边界、调用次数、失败停止和重入。它不模拟真实 eMMC 时序，不证明寄存器顺序在板上正确。另一个 `tools/testing/sunxi-mmc-panic-hw.py` 从真实硬件辅助代码与本树宏定义生成原生 C 模拟程序，检查 PIO 字节顺序、CMD13 错误/超时、累计中断完成状态、硬件超时与软件到期的分流，以及读写中止的不同 FIFO 操作。

```sh
python3 tools/testing/sunxi-mmc-panic-interface.py \
    --source drivers/mmc/host/sunxi-mmc.c
python3 tools/testing/sunxi-mmc-panic-hw.py
```

本次已运行两份脚本并通过，且 `git diff --check` 通过。原树 checkpatch 与本机 Perl 不兼容，使用工作区较新内核的 checkpatch 代查，驱动补丁无 error；保留一条针对 `spin_is_locked()` 的提示，因为这里要检测并拒绝占用，不能换成要求“当前应当持锁”的 lockdep 断言。头文件检查通过。

在 Linux 构建机使用实际产品配置与匹配工具链，至少编译目标文件：

```sh
make ARCH=arm CROSS_COMPILE=/path/to/arm-linux-gnueabihf- \
     drivers/mmc/host/sunxi-mmc.o
```

随后做完整内核链接，确认导出符号与配置依赖。需检查 `CONFIG_MMC_SUNXI=y`、`CONFIG_ARM_ARCH_TIMER=y` 以及产品真实的 T3 配置；不把参考 defconfig 当成产品配置。

### 回归矩阵

所有破坏性测试都应在已经核对、独占的日志测试区进行。下面是应执行的板测计划，本次未代替用户执行：

| 场景 | 应核对结果 |
| --- | --- |
| 未接入上层、正常启动 | 不自动写日志区，无测试 sysfs 和自动 panic |
| prepare 后不发生 panic | 普通 eMMC 读写保持正常；准备不写日志扇区 |
| 空闲时 panic 写 512/4096 字节 | 重启读回逐字节一致 |
| 同一 panic 连续两次 write | 第二次地址正确，不再次处理旧 mrq |
| 区域第一个/最后一个扇区 | 仅目标区域改变，相邻哨兵不变 |
| 非对齐 buf、非法长度、范围越界 | 非对齐地址合法；非法参数不发硬件写 |
| 原 CMD17/CMD24 尚未完成 | 完成后接管；超时不盲目中止单块请求 |
| 原 CMD18/CMD25 自然完成 | 正常收尾，不多发手工 STOP |
| 原 CMD18/CMD25 软件等待超时 | 分别验证 DMA reset、读 drain、写 busy/FIFO reset |
| panic 前已经处理部分 IRQ | 合并 int_sum 后仍识别旧请求完成 |
| 控制器硬件超时、CRC/IDMAC 错误 | 返回失败，后续调用不继续写 |
| host lock、重试、busy、manual-stop 阶段 | 按契约拒绝接管 |
| sbc、cache、硬件分区或时序不支持 | 明确失败，不猜测支持 |
| 暂停/恢复、时钟配置变化 | 不在未满足条件时写硬件 |
| 写入过程中复位/断电 | 上层扫描拒绝残缺记录 |

此前的上板测试提供了设计依据；重构后的代码仍需复测这些分支。尤其要覆盖普通 I/O 压力下随机发生的 panic，因为旧测试注入点通常刻意选在比较容易接管的位置。

## 20. 阅读源码的推荐顺序

先看头文件三个声明，再看公开 `prepare/write/unprepare`，然后从 write 调用到 `takeover` 和 `write_sector`。理解主线后，再进入 pending、DMA reset 和 STOP 辅助函数。

进一步核对本地依据：

- `drivers/mmc/host/sunxi-mmc.c`：正常 IRQ/request 流程与本次接口实现。
- `drivers/mmc/host/sunxi-mmc.h`：寄存器偏移、位定义与 host 字段。
- `drivers/mmc/core/host.c`：时钟 hold/release 的实现。
- `drivers/mmc/core/core.c`：普通请求等待流程。
- `kernel/panic.c`：关闭本地中断、停止其他 CPU 和 kmsg dump 的顺序。
- `include/linux/pstore.h`、`fs/pstore/platform.c`：本版本真实的后端契约。

这样阅读时，每个辅助函数都有一个明确目的：为下一步建立可检查的硬件前提，而不只是一串需要死记的寄存器操作。
